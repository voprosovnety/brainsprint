The comparison preserves the original price audit; account-specific findings below supersede proposals. deployment instructions for the existing package remain in [DEPLOYMENT.md](DEPLOYMENT.md). ## Free-first correction

The approved deployment budget is strictly **$0/month**, with permanent Free plans, no paid add-ons, no trial-credit dependency, and no automatic paid overage. Paid options below are retained as historical research and are outside this authorization.

Vercel's [Container Runtime](https://vercel.com/docs/functions/runtimes/container) is in beta on all plans and uses Function pricing, but its Dockerfile deployment builds and pushes the image to Vercel Container Registry. The registry's [pricing page](https://vercel.com/docs/container-registry/limits-and-pricing), rechecked on 2026-10-20, lists **$0.10/GB image storage** and does not list a Hobby free storage allowance. Availability on Hobby is therefore not proof of a $0 container deployment. Do not create billable registry resources unless an actual account explicitly establishes a permanent free allowance; absent that evidence, use a different backend.

The selected package is **Vercel Hobby Next.js + pinned community Vercel PHP Laravel + Neon Free PostgreSQL 17**. It uses ordinary PHP functions and no billable container registry. The existing Laravel boundaries, Filament assets, PostgreSQL persistence and same-origin proxy are retained; shared function locks/rate budgets use PostgreSQL. The community runtime is an additional deployment dependency, so its pinned version and PHP/libpq compatibility must be maintained. See [its source](https://github.com/vercel-community/php) and the configuration in DEPLOYMENT.md.

Actual account provisioning superseded the earlier Render recommendation: **Render requires credit-card identity verification even for Free in this account**, so no Render service is used. serv00 remains an alternative subject to manual registration (its terms prohibit automated account creation), application review and owner login within 90 days. No artificial keep-alive is permitted. Account state, actual public URLs and completed checks are recorded only in IMPLEMENTATION_PLAN.md.

## Actual application requirements

- `apps/web`: Next.js 16.4.2 / React 19.3.1; Node 22+, with Node 24 used by CI. It requires a Node runtime for its same-origin API route; a static export would remove necessary functionality.
- `apps/api`: Laravel 13.37.0, Filament 5.10.2 / Livewire 4.4.7; PHP 8.3+ with PostgreSQL and the extensions installed by the existing production Dockerfile. PHP 8.5 is already packaged. Filament is read-only: funnel configuration is published from the versioned JSON source using the existing seeder.
- PostgreSQL 17 is the current local/CI baseline. Runs, events, immutable configurations and both consumer/admin sessions live in PostgreSQL. Keep that baseline for the proposed Neon or VPS database.
- No Redis, separate worker, queue service, object storage or mail service is needed. Ordinary PHP requests, one backend replica and local shared lock/rate-limit files match the current design. Ephemeral application storage is acceptable; database storage must persist.
- An existing Apache/PHP production image, runtime secret validation, secure cookies, proxy authentication and explicit release/admin commands already exist. There is no need to rebuild the application or alter funnel business rules.
- The Next.js upstream timeout is **12 seconds** (`apps/web/src/app/api/[...path]/route.ts`); public analytics also has a 14-second client timeout. A minute-long backend wake-up would produce an unavailable response with the existing code.

Resource estimates are engineering judgments, **not measured hosting results**. A 512 MB PHP container needs strict concurrency limits; 1 GB is a more practical Laravel-only VPS target. Approximately 2 GB is a reasonable starting point for Next.js + Laravel + PostgreSQL together at demo traffic. Build artifacts off the small VPS, limit PHP workers and database connections, and verify memory after deployment before describing capacity as proven. The PHP per-request limit of 192 MB is not a measurement of total server memory.

## Free-tier limitations that affect this project

**Vercel.** Hobby is for personal, noncommercial projects, with quota exhaustion causing feature suspension rather than an automatic paid upgrade. This proposal assumes a personal demonstration with no sales. Hobby includes 4 active CPU-hours and 1 million function invocations; application analytics remains in Laravel, independent of Vercel analytics. Git-based deployment and a free HTTPS `vercel.app` address are available. Function initialization latency remains possible, but there is no Render-style minute-long application sleep. Eligibility and deployment protection must be checked before release: the production demo must open without a Vercel login. Sources: [Hobby](https://vercel.com/docs/plans/hobby), [plan limits](https://vercel.com/docs/limits), [fair use](https://vercel.com/docs/limits/fair-use-guidelines).

**Render.** Its 750 free instance-hours are shared per workspace/month; one continuously running service fits even a 31-day month, while multiple services can exhaust the pool. Free instances have no persistent disk, shell/SSH, one-off jobs or paid pre-deploy command. Keep PostgreSQL on Neon: Render's own free PostgreSQL expires after 30 days. Migration/admin provisioning would require a deliberate external operator job or another reviewed release mechanism; do not blindly add migrations to every boot. Free services can restart unexpectedly. Without a payment method, billable overage disables services; with a saved method, bandwidth/build overage can be charged. Sources: [free limitations](https://render.com/docs/free), [billing FAQ](https://render.com/docs/faq), [pre-deploy availability](https://render.com/docs/deploys).

**Neon.** The current Free plan includes **1 GB PostgreSQL storage, 100 CU-hours and 5 GB outbound transfer per project/month**, with no card required. Older 0.5 GB/50 CU-hour articles are outdated. At a fixed 0.25 CU, 100 CU-hours means 400 active database hours, not 24/7 availability under continuous query load. Sleep after five idle minutes is mandatory; automatic wake is advertised as a few hundred milliseconds, not a guaranteed end-to-end request time. No Render-style 30-day database expiration is listed. Free limits can interrupt service; the short restore window is not a replacement for independent backups. Sources: [current plan](https://neon.com/docs/introduction/plans), [October storage increase](https://neon.com/blog/neon-free-plan-1-gb-per-project), [scale to zero](https://neon.com/docs/introduction/scale-to-zero), [no-card signup](https://neon.com/blog/neon-works-with-stripe-projects-for-agentic-provisioning).

**serv00.** PHP through 8.5, SSH, HTTPS, a free `login.serv00.net` hostname and PostgreSQL are advertised. Native PostgreSQL is version 16; the proposal uses Neon to retain the project's PostgreSQL 17 baseline and separate data from the hosting account. Deployment would use native PHP with the web root pointing only at Laravel's `public/`, rather than Docker. The explicit fatal caveat: **90 days without an owner login through the panel or SSH permanently deletes the account**. Website visits do not satisfy this rule. Backups are not guaranteed; no SLA is provided, and account approval/capacity/CPU throughput are not guaranteed. Configure PHP extensions, rewrite rules and provider request protections, and verify that server-to-server JSON requests pass without an interactive challenge. No fake keep-alive is proposed. Sources: [offer](https://www.serv00.com/), [terms](https://www.serv00.com/terms-of-service/), [PHP](https://docs.serv00.com/PHP/), [signup](https://www.serv00.com/register-account/).

## Other investigated alternatives

- **Northflank Sandbox:** official pricing offers two always-on free services and one database, so technically promising. However, [billing documentation](https://northflank.com/docs/v1/application/billing/pricing-on-northflank) requires a payment method before resource creation on **every** plan. Not a verified solution for an owner without a usable international payment method. [Pricing](https://northflank.com/pricing).
- **alwaysdata Free:** currently advertises 1 GB SSD / 256 MB RAM / 0.25 CPU, lifetime personal hosting. However, the actual [Free registration form](https://www.alwaysdata.com/en/register/?p=2012) in this audit required card validation and disabled account creation until validation, despite marketing saying no card. An exception via support is unconfirmed. It also suspends new free profiles after 120 days without an administration login. Not selected. [Offer](https://www.alwaysdata.com/en/offers/), [inactivity policy](https://help.alwaysdata.com/en/docs/admin-billing/profile/suspension/).
- **Cloudflare Containers:** product marketing shows included usage, but [the detailed pricing documentation](https://developers.cloudflare.com/containers/platform/pricing/) places it inside the **$5/month Workers Paid plan**. Not a $0 backend and not selected under the payment constraints.
- **VDSina:** [standard tariffs](https://vdsina.ru/pricing/standard) advertise 1 CPU / 1 GB / 10 GB at 5 RUB/day and a 2 GB tier at 20 RUB/day. A current complete IPv4-inclusive order price and suitable Russian payment path were not both established in this audit, so the 150 RUB headline is not treated as a confirmed deployable total. **VDSka:** its current price page could not be loaded reliably; no unverified old-page price is used.
- The repository's existing Railway option is an earlier paid deployment baseline, not an approved spend or a demonstrated $0 solution. It is not the recommendation under the new constraints. Temporary promotional/trial credits are not counted as free hosting.

The VPS column's HTTPS is **not included as a preconfigured provider service**. A free name such as `api.<public-ip>.sslip.io` can resolve to the VPS without buying a domain; Caddy/ACME can obtain and renew its own certificate. This adds a free DNS dependency and shared certificate-rate-limit risk. A provider technical name, if actually available for this account, or another approved free DNS name can be used instead. No name is reserved yet. Source: [sslip.io DNS and TLS documentation](https://sslip.io/).

All suggested public demo pages are intended to open without hosting-account authentication; Filament alone retains its separate administrator login. An always-on VPS still needs restart-on-failure, OS security updates, certificate renewal, bounded log/disk growth and real backup/restore procedures. It does not eliminate outages or create an SLA for the application.

No provider here is represented as reachable from every country/network. Vercel documents [ISP and network blocking](https://vercel.com/kb/guide/how-to-resolve-ip-blocking-issues); FirstVDS warns about some [Russia-to-Netherlands/Kazakhstan reachability](https://firstvds.ru/products/vds_vps_hosting). Choose Moscow for the proposed low-price SSD VPS and place serverless frontend functions and Neon in compatible nearby European regions. International free-provider registration/anti-abuse approval remains account-specific. Current public pages were researched from this environment, **not tested from Russian or employer networks**. If the intended employer cannot reliably reach `vercel.app`, prefer the all-on-VPS alternative; asking the employer to use a VPN is not an acceptable demo requirement.

GitHub Actions private-repository minutes/storage must remain within the account's included allowance with paid overage disabled; the account's remaining quota has not been inspected. The historical comparison preceded the controlled Vercel release workflow described in DEPLOYMENT.md. Automatic code deployment must keep migration/publication ordering deliberate, protect secrets and isolate previews from production. Synthetic analytics samples age out of the current seven-day view; a genuine daily maintenance job can refresh the sample idempotently and run bounded retention. These are application maintenance operations, not artificial traffic intended to defeat provider sleep.

## Recommendation and budget tiers

Use permanent Free plans only. The Vercel-container candidate fails the documented $0 registry requirement unless account-specific evidence resolves it. The selected architecture uses Vercel Hobby Next.js and community PHP functions plus Neon Free; Render was excluded after actual card verification was required. serv00 offers a different tradeoff with registration review and the 90-day owner-login deletion rule. The paid tiers below are historical comparisons, not approved alternatives.

- **$0:** Vercel Hobby frontend and community PHP backend, Neon Free PostgreSQL 17, exact server-only origins/secrets, and explicit GitHub release/maintenance jobs. Free quotas and personal noncommercial restrictions apply.
- **Up to 300 RUB/month:** the proposed 299 RUB hybrid; free frontend/database quotas and regional reachability remain real limitations.
- **Up to 500 RUB/month:** keep the same configuration. Spending 349 RUB on the researched RUVDS SSD does not establish a material benefit. No need to consume the full budget.
- **Up to 1,000 RUB/month:** 519 RUB FirstVDS 2 GB for the entire stack eliminates Vercel/Neon quotas and their account dependencies; 919 RUB buys 4 GB / 2 CPU / 60 GB SSD if later memory measurements justify it. Do not upgrade without approval.

The **299 RUB total** includes the selected VPS and IPv4; Vercel/Neon Free, certificates and DNS add zero within their allowances. It excludes **unselected optional paid** panels, managed backups and extra resources. Plan encrypted database dumps on the already-paid VPS storage plus an independent owner-controlled copy and a restore rehearsal; agree the destination and retention before release. Do not silently enable paid backup products. The 519 RUB all-on-VPS alternative similarly excludes optional paid backup services.

Within the authorized $0 public-deployment scope, the necessary work is: authorized provider/GitHub access; verify actual Free plans, remaining quotas and overage behavior; configure exact origins and runtime secrets privately; minimally adapt deployment packaging; create a new release database; run explicit migrations/publication/sample seed; provision the separate admin using its secret-file command; configure TLS, backups and real maintenance; add controlled GitHub deployment; verify public mobile/desktop flows, cookies, CSRF, origin rejection, persistence, ownership, stable assignment, event deduplication, deletion and Filament isolation. Never run test suites against production or migrate/reset the existing local development history.

The initial price audit read repository files and official provider material without performing deployment checks. Subsequent implementation and real-provider acceptance are recorded in IMPLEMENTATION_PLAN.md; this comparison does not duplicate current task status.
